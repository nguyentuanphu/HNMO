# Plan: Season 6.3 and Season 9 side by side (2026-11-19 21:45 Sydney)

Goal: each season plays by its own server rules, the admin panel shows them apart, and the web game draws each
season's look correctly. Branch from `origin/claude/hnmo-main-handover-54co2m`; draft PRs into it, one per step.

## Answer to "use the Season 9 client for Season 6 and borrow its files"

No, not wholesale. About 7,300 Season 9 files that share a name with a Season 6 file are different (the player
model, most monsters, items and maps), so Season 6 would stop looking like Season 6, and the Season 9 `Local/` and
`Interface/` files are other formats that break the windows. What does work: one web client for both seasons
(it already is one), where a Season 6 world takes from the Season 9 pack only what Season 6 does not have at all
(the Season 9-only maps and their models), and every file Season 6 has stays its own.

## Step 1: two configurations in one database (about 1.5 days)

Storage choice: **one database, one configuration per season**, not one database per world.
- The data model already has it: every game server record points to the configuration it loads
  (`GameServerDefinition.GameConfiguration`); today they all point to the same one.
- Shared things stay in one place without copying: accounts, coins and top-ups, website, admin users, chat filter,
  licences, host settings, the shared state file. A database per world would need all of that kept in sync.
- Season settings are what the configuration holds: maps and gates, monsters and spawns, items and drop bags, chaos
  mixes, skills and classes, rates, mini-games and events, plug-in settings (season plan included), cash shop
  catalogue (its items are season items; the coin balances stay shared).

Work:
1. Mark each configuration with its season (a `Season` field on the configuration, with a database migration).
   Today's configuration becomes Season 6.3, unchanged.
2. Create the Season 9 configuration as a full copy of Season 6.3 (the configuration copy code exists), so Season 9
   starts playable; the Season 9 import then fills it (it no longer writes into the shared one).
3. Each game server loads the configuration of its world's season: saving a world on the Worlds page points its
   servers at that season's configuration. The start-up data source learns to hold two configurations.
4. Characters belong to a season: a character's class and items come from its season's configuration, so character
   select on a Season 9 server shows only Season 9 characters, and creating one uses Season 9 classes.
5. Tests: a server of each season loads only its own settings; editing Season 9 never changes Season 6; today's
   save upgrades to "Season 6.3" with nothing lost (counts of items, maps, monsters, plug-in settings before/after).


### Correction (2026-11-19 23:00 Sydney): one database per season, not two configurations in one

Checked in the code: the game data uses fixed ids (`GuidHelper.CreateGuid<T>(number)` in
`Persistence/Initialization`): the same item, map or monster has the same id in every configuration made from the
data. Two full configurations can't share one database (their ids collide), and a copy with new ids would break
the code that looks entities up by those ids. Also, all game servers share one plug-in manager, and the admin panel
edits one configuration everywhere.

So step 1 becomes:
- **One database per season**: `hnmo` stays Season 6.3; a new `hnmo_s9` holds Season 9 (made by the Season 6
  initializer, then the Season 9 import). The per-world database code that exists (WorldRegistryService) is the
  base for it.
- **Each season's game servers** run with that database's configuration and their own plug-in manager.
- **Shared between seasons**: logins (an account made in one season exists in the other; passwords stay in step),
  coins (one balance: the cash-shop balance moves to the shared store, or the second database reads it from the
  first), the website, admin users, host settings, news, bans. Characters, vaults and items stay per season (owner's
  decisions 1 and 2 fit this).
- This is the largest piece: about 2 to 3 days instead of 1.5, and it needs the owner's OK on the shared-coins
  approach before it starts.
